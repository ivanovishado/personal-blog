AI makes mediocrity cheap.

That changes the shape of software engineering more than the replacement discourse does. If a model can turn a vague ticket into a respectable first draft in minutes, then "I can produce acceptable code quickly" is no longer a durable advantage. Acceptable output is abundant now. Judgment is not.

I use coding agents every day. Claude Code does real work for me, and I have written about [how I constrain it with hooks](/en/deterministic-claude-code-setup/) and [how I keep its instructions lean](/en/whats-in-my-claude-md/). Those systems exist for one reason: the model is already strong enough at the mechanical part of the job that the real risk has moved elsewhere. The risk is letting plausible output pass for good engineering.

## What changed?

The scarce resource is no longer the first draft. In a decent codebase, a model can usually scaffold the route, wire the form, write the validation, add tests, and produce a clean explanation before a human would have finished the boring part by hand.

That used to carry more prestige because it used to absorb more labor. Teams could distinguish themselves just by getting to "working" faster than everyone else. The new baseline is higher, and that compresses the value of average implementation work.

This does not mean the hard parts vanished. It means the hard parts moved upstream and downstream.

Upstream, you have to define the problem well enough that the model does not sprint in the wrong direction. Downstream, you have to review the result with enough discipline to catch the ways it worsened the system while still looking tidy on screen.

In my own workflow, the interesting part is rarely whether Claude Code can produce a route handler or a decent test file. It usually can. The value comes from refusing the extra helper it invented, rewriting the names, shrinking the diff, or forcing it to handle the awkward state transition it skipped. The tool saves me time precisely because I spend that time on judgment instead of typing.

## What does mediocre AI-assisted work look like?

Mediocre AI-assisted work usually passes the easy checks. The code compiles. The tests are green. The UI matches the screenshot. The pull request summary sounds thoughtful. Then somebody has to maintain the change, debug a weird case, or extend it a month later.

At work, I once used AI to help implement a query over hierarchical data that had to find related elements inside the same structure. The query looked good on paper and passed the obvious checks. Then we landed it in TEST with real input, and interaction latency spiked because of how the traversal behaved under realistic load.

The fix was not to throw the query away. I worked with the model again, reorganized the internal data structures for faster retrieval, and cut the memory cost enough that the UI stopped paying for the backend shortcut. A weaker engineer could have let it slide because the core functionality still worked.

None of that is catastrophic in isolation. That is why it slips through. The code is usually good enough to merge and annoying enough to live with. A human with weak standards can now produce far more of that kind of damage per day than before.

When people talk about AI slop, I do not mean all generated code. I mean generated code that is accepted because it looks finished. A long diff, a polished explanation, or a fast demo can create the illusion of engineering progress. Visible motion is not the same thing as a sound decision.

## Where does judgment actually show up?

Judgment shows up before the prompt, during review, and in what you choose to delete.

Before the prompt, it shows up in problem framing. Weak engineers hand the model the first implementation idea that comes to mind. Strong engineers spend time shrinking the task, clarifying constraints, and removing ambiguity before the model writes a line. A smaller, sharper task is not only easier for the model; it is easier for the human to evaluate afterward.

During review, judgment shows up in the questions you ask. Did this solve the problem or just complete the ticket literally? Did the code get simpler, or did it just get more organized-looking? Did we improve the state model, failure handling, and boundaries, or did we only improve the screenshot and the prose in the PR description?

It also shows up in deletion. Models have a bias toward more: more wrappers, more helper functions, more abstractions, more explanatory comments, more tests, more words. Sometimes that extra structure is warranted. Often it is camouflage. Strong engineers are willing to throw away a third of a generated diff if the result becomes easier to read, easier to trace, and easier to change.

This is where "taste" stops being mystical. Taste is not a vibe. It is the ability to feel friction early. A name that hides two concepts. A helper that only exists because the generated code got tangled. A test suite that certifies the implementation instead of the behavior. A neat abstraction that makes the next change harder, not easier.

## What do strong engineers do differently?

Strong engineers still get more leverage from the same tools, but the leverage comes from a different place now. It is less about typing speed and more about maintaining standards inside a faster loop.

They constrain the model. They say what cannot move, which failure cases matter, what tradeoffs are unacceptable, and where the code must stay boring. Without that pressure, the model fills the empty space with plausible garbage.

They review for system cost, not just local correctness. A change can work and still make the codebase worse. Good engineers notice when a tiny feature added a second concept to a module, introduced a new source of truth, or increased the mental overhead of following a request through the stack.

They verify behavior instead of trusting fluency. Models sound done long before the work is done. The explanation is rarely the problem. The problem is the hidden assumption under the explanation.

They keep ownership. If a change breaks in production, nobody cares that the model drafted it. The responsibility does not move just because the typing did.

## What would I look for in a review?

When an AI-generated diff lands in front of me, these are the questions that matter.

- Did we solve the right problem, or did we overfit to the wording of the ticket?
- Is the code smaller or clearer than the version a disciplined human would have written?
- Did the change introduce a new abstraction, file, or helper that now has to justify its existence?
- Are the error paths, retries, loading states, and edge cases as well handled as the happy path?
- Do the tests validate behavior independently, or do they simply mirror the model's structure?
- Is the naming precise enough that another engineer can trace the intent without reading everything?

That checklist is not glamorous. That is the point. Most quality failures in AI-assisted work are not exotic. They are ordinary review failures happening at a higher volume.

You do not need superhuman prompting to catch them. You need enough discipline to slow down at the exact moment the tool is trying to make speed feel like adequacy.

## What does reality testing catch that review misses?

Review catches a lot, but it still happens before the software meets real use. Dogfooding is not a separate virtue here. It is one of the places judgment proves itself against reality. It is where you find the failures the model never had a reason to simulate.

On a personal project, I used one AI tool to generate the designs and another agentic model to implement and validate the UI. The result matched the designs, the browser-based checks passed, and navigation looked fine. Then I actually used the site and hit the paths the agent had not exercised: rate limits, permission differences, and the messy sequence of actions a real user takes when they are not following a happy path.

Those failures were not surprising. They were just outside the slice of reality the agent had tested. I fixed them with the model, but the useful part was finding them by using the product instead of admiring the screenshot.

## What loop has worked best for me?

The loop that keeps paying off is simple: draft, dogfood, document, repeat.

- Draft with the model until you have a serious first pass, not a toy.
- Dogfood the result with realistic data, permissions, limits, and workflows until reality pushes back.
- Document the failures and the fixes so future agents and engineers do not have to relearn the same lesson from scratch.
- Repeat with the sharper understanding you earned from actual use.

If a loop keeps making the work better, encode it into your team's process so the next engineer starts from a higher standard.

## Why should this make engineers uncomfortable?

AI removes some of the old excuses.

If the model can handle a meaningful share of the repetitive implementation work, then there is less cover for muddy naming, oversized diffs, fragile state handling, and tests that only exercise the photogenic path. Teams still have deadlines. Businesses still need rough versions sometimes. Shipping constraints did not disappear.

But the old "I was buried in the mechanical work" defense has less force than it did even two years ago. The machine is helping with the mechanical work. If the outcome is still sloppy, we should look harder at the human decisions around scope, review, and standards.

I think that is good news, even if it is uncomfortable. It means the craft part of software engineering matters more, not less. The job is moving toward clearer thinking, firmer boundaries, better review, and better refusal. Those are durable skills.

## What should ambitious engineers optimize for now?

I would optimize for problem framing, simplicity, and review quality.

Problem framing matters because most wasted effort starts before implementation. If the task is vague, oversized, or based on the wrong abstraction, the model will still give you something polished enough to seduce you.

Simplicity matters because generated code tends to expand. Someone has to keep asking whether the code can be shorter, flatter, and easier to reason about without getting cute.

Review quality matters because AI compresses the time between idea and diff. If your review habits are weak, you can approve a lot of bad structure very quickly. If your review habits are strong, you can remove weeks of mechanical work without lowering the bar. That review should include dogfooding under realistic constraints, not just reading the code and nodding at the diff.

The opportunity is real. A strong engineer with a strong model can cut huge amounts of routine effort and spend the saved time on the decisions that actually compound: naming, boundaries, migration safety, operability, and the ugly cases that only show up once real users touch the thing.

That is a much better bargain than competing with the model on raw output.

## Excellence is still the job

AI can get almost anyone close to average output faster than before. That is exactly why average output matters less.

The bar did not disappear. More people can reach it. The work that stands out now is the work with clearer scope, simpler structure, better failure handling, better naming, and better judgment about what should never have been built in the first place.

That is the standard I care about. The machine can already produce code that looks competent. The real question is whether we can still tell the difference between a fast draft and engineering that deserves to survive first contact with reality.
